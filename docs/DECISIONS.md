# Implementation decisions and deviations from ARCHITECTURE.md

Where the implementation intentionally differs from, or fills a gap in, `ARCHITECTURE.md`, it is recorded here.

## Gateway engine

| # | Decision | Why |
|---|---|---|
| I1 | Global flow caps lowered to **2048 TCP / 1024 UDP** (per-client caps unchanged: 1024 / 512); gVisor TCP send/receive buffers fixed at **256 KiB** each, auto-tuning off (`gwstack.Limits.TCPBufferSize`). | gVisor's defaults (1 MiB, auto-tuned to 4 MiB per direction) let one malicious member exhaust gateway memory with stalled flows. Worst case is now ≈1.3 GiB. Throughput per connection ≈ 256 KiB/RTT (≈40 Mbit/s at 50 ms RTT; LAN unaffected). |
| I2 | Integration tests reach a local test server by sending to TEST-NET `192.0.2.1` and redirecting the dial to `127.0.0.1` (test-only knob, guarded by `testing.Testing()`), instead of allowing loopback. | gVisor drops loopback-addressed packets on both ends; loopback stays denied in every build. |
| I3 | gVisor's own logging is disabled process-wide. | It writes to stderr by default (no-logs rule). |
| I4 | The gateway also adds its own interface addresses to the deny list itself, in addition to `ExtraDeny`. | Defence in depth for D13. |
| I5 | DNS forwarder: ≤ 64 upstream queries in flight per client; the next upstream is raced after 1 s. | Bounds fd/goroutine use per member. |

## Control plane and discovery

| # | Decision | Why |
|---|---|---|
| I6 | Per-source state table evicts least-recently-seen sources when full (instead of refusing new sources). | A spoofed-source flood must not lock out new joins. |
| I7 | Global INFO limit 20/s (burst 40) in addition to the per-source limit. | §6.6; INFO is the most expensive request. |
| I8 | An unverified beacon may downgrade a verified entry only when it comes from an address the entry was verified at, and only after verified beacons stopped for > 10 s. Forged endpoints are dropped when an entry becomes verified. | Prevents LAN spoofing from flipping member gateways to "locked" or steering JOINs to an attacker's address. |
| I9 | **Accepted risk:** members share `K_ctrl`, so a member on the same LAN can read another member's JOIN_RESP lease token and send LEAVE for it (eviction; no traffic access, WireGuard keys are per session). | Inherent to the single-network-key design (§4 T3); per-session control keys are a v1.1 candidate. |

## Client tunnels and helper

| # | Decision | Why |
|---|---|---|
| I10 | Windows DNS-leak protection uses Private VPN Pro's own WFP filters (block port 53 except to the tunnel resolver and from `private-vpn-pro.exe`) in a dynamic WFP session that disappears with the helper process. | `wireguard-windows/tunnel/firewall.EnableFirewall` installs no DNS filters with `doNotRestrict=true` and requires a service SID that a UAC-elevated helper does not have. |
| I11 | The helper is launched with `ShellExecuteExW` (not `ShellExecute`) and the client verifies the pipe server's PID. | Detects pipe squatting and helper exit. |
| I12 | macOS DNS backup lives in `/Library/Application Support/Private VPN Pro/run/dns-backup.json` (root-owned, 0600). | The root helper must not write through user-controlled paths; the backup must survive a reboot. |
| I13 | Endpoint `/32` exclusion routes are tagged (Windows metric 5056, macOS `-proto2`) and swept at the next helper start; they are added only when no route more specific than `/1` already covers the endpoint. | Crash cleanup without ever writing addresses to disk. |
| I14 | Linux: `src_valid_mark=1`; `resolvectl` only when `/etc/resolv.conf` really points at systemd-resolved; DNS failures are non-fatal in the `setcap` path. | Matches wg-quick; a capability-only process cannot write `/etc`. |
| I15 | The main binary refuses every subcommand except `tunnel-helper` when `PKEXEC_UID` is set, and refuses to run the app as root on macOS/Linux. | `auth_admin_keep` would otherwise let same-user processes re-run privileged commands without a prompt. |
| I16 | **Linux dual role** (gateway and client at once) requires `CAP_NET_ADMIN` on the binary (`sudo setcap cap_net_admin+ep private-vpn-pro`); without it the engine refuses the combination with a clear error. Single roles are unaffected. | `SO_MARK` (needed so forwarded traffic bypasses the client tunnel) needs the capability. |
| I17 | In dual role, the gateway's DNS forwarder skips private/loopback system resolvers and uses public fallbacks (1.1.1.1, 9.9.9.9) over the physical interface. | §8.6's "resolvers saved by the helper" are not exposed through `tunnel.Tunnel` in v1. |

| I24 | **Fail-closed kill switch** (`tunnel.Config.KillSwitch`): an OS-level block of everything that does not go through the tunnel — Windows: WFP filters (block at ALE_AUTH_CONNECT/RECV_ACCEPT v4+v6; permits for `private-vpn-pro.exe`, the tunnel LUID, loopback, the gateway endpoint IP (any port/protocol), DHCP/DHCPv6/NDP, DNS to the tunnel resolver only, LAN with `allow_lan`); macOS: a pf ruleset in anchor `com.apple/100.PrivateVPNPro` with the same permits; Linux: wg-quick policy routing plus `blackhole default` (metric 20566) in table 20566 and DNS confinement rules (`ipproto udp/tcp dport 53 blackhole`, prio 20563; marked sockets and the tunnel resolver exempted at 20561/20562). It is installed **before** any route and replaced atomically (one WFP transaction / one `pfctl -f` / add-then-delete rules) on re-Up and SetEndpoint. It **survives the helper, the app and a reboot**; only an explicit `Down` (helper `down`, idempotent, works with nothing up) or `private-vpn-pro unblock` removes it. `Close()` (helper exit, pipe closed, engine failure paths) removes the tunnel and keeps the block. | The user's requirement: a dropped tunnel must never fall back to the real IP, including across a crash or a restart before the app reconnects. |
| I25 | macOS uses **pf**, not route blackholes. | At boot there is no default route, so a /32 for the endpoint cannot be installed and a route-based block would make reconnecting impossible; pf is route-agnostic, also stops interface-bound sockets and can enforce `allow_lan=false`. Rules are `quick` + `no state` and the state table is flushed on install so no earlier flow bypasses them. pf is enabled with `pfctl -E` and left enabled (stock `/etc/pf.conf` passes everything). |
| I26 | **Boot persistence**: Windows — provider, sublayer and filters carry `FWPM_*_FLAG_PERSISTENT` with fixed GUIDs / deterministic filter keys, enforced by BFE from boot; macOS — `/Library/LaunchDaemons/app.privatevpnpro.killswitch.plist` (RunAtLoad) runs a **root-owned copy** of the binary at `/Library/Application Support/Private VPN Pro/bin/private-vpn-pro killswitch-boot`; Linux — `/etc/systemd/system/private-vpn-pro-killswitch.service` (oneshot, `Before=network-pre.target`, wanted by `sysinit.target`) runs `/var/lib/private-vpn-pro/bin/private-vpn-pro killswitch-boot`. The boot block is the live one minus the tunnel interface. The record it needs (`killswitch.json`, root 0600: endpoint IP + `allow_lan`, nothing else) lives in `/Library/Application Support/Private VPN Pro/run` / `/var/lib/private-vpn-pro`. Without systemd / without root (setcap path) the tunnel reports `kill_switch_not_persistent`. | The daemon must not execute a user-writable binary as root; copying it into a root-only directory removes that path. Everything is removed by `Down`/`unblock`. |
| I27 | `Status.Warnings` codes: `ipv6_not_blocked`, `dns_not_set`, `kill_switch_failed`, `kill_switch_not_persistent`, `lan_not_blocked` (Linux: policy routing cannot keep on-link LANs out), `dns_not_blocked` (Linux kernel/iproute2 < 4.17: no fib-rule port matching). `Status.KillSwitchActive` reports the block. `helper.Client.Down` launches a helper when none runs (the engine creates a fresh Client to lift a leftover block) and reports `ErrHelperGone` after the helper died; `Client.Close` never lifts the block. | Honest reporting instead of silent logging; the engine shows the codes as problems. |
| I28 | Android: `Up` establishes the new VpnService interface before closing the old device (no interface-less moment on a rebuild); `Down` always calls `closeTun` (also from a fresh Tunnel after a lost session) and is idempotent; `Close` keeps the interface (a failed session stays blocked, the orphaned device shuts down when the interface is revoked). The detached fd is closed explicitly when `SetNonblock` fails before wireguard-go wraps it. | The VPN interface is Android's kill switch. |
| I29 | **Recovery when the app cannot do it** (deleted app, broken helper): `private-vpn-pro unblock` as administrator / `sudo`. On macOS the daemon's copy works too: `sudo "/Library/Application Support/Private VPN Pro/bin/private-vpn-pro" unblock`; by hand: `sudo launchctl bootout system/app.privatevpnpro.killswitch; sudo rm /Library/LaunchDaemons/app.privatevpnpro.killswitch.plist "/Library/Application Support/Private VPN Pro/run/killswitch.json"; sudo pfctl -a com.apple/100.PrivateVPNPro -F rules`, then restore DNS in System Settings (or `sudo networksetup -setdnsservers <service> Empty`). Linux by hand: `sudo systemctl disable --now private-vpn-pro-killswitch; sudo rm /etc/systemd/system/private-vpn-pro-killswitch.service /var/lib/private-vpn-pro/killswitch.json; sudo ip rule del priority 2056{1..6}` (repeat until gone, `-6` too); `sudo ip route flush table 20566`; restore `/etc/resolv.conf` from `/etc/resolv.conf.private-vpn-pro-backup`. Windows has no built-in tool that deletes third-party persistent WFP filters, so while the kill switch is engaged the helper keeps an administrator-only copy at `%ProgramFiles%\Private VPN Pro\recovery\private-vpn-pro.exe`; run it as administrator with `unblock` (also works after the app was uninstalled; `netsh wfp show filters` lists the objects for diagnosis). A reboot alone does **not** lift the block (by design). | Documented manual recovery for every OS. |
| I30 | **Resume after a restart, honestly.** The resume target (`client.resume_gateway_id`) is recorded as soon as a tunnel exists for a gateway (not only after the first handshake): a session whose gateway never answered WireGuard is still one the user wanted back, and its block is engaged. `resumeLoop` retries JOIN quietly, but stops after any failure at or beyond the tunnel stage (`elevation_needed`: prompt declined; `internal`: the OS refused the tunnel) — every retry would be another administrator prompt. `status.client.resume_pending` reflects the loop itself (true while it runs or its own attempt is in flight), so once it gave up the UI/tray stop saying "reconnecting" and show the engaged block plus *why* the reconnect failed (both problems are listed). `--autostart` launches resume the last session like every other start (the earlier "never connect a tunnel" text was stale). | A UI that promises an automatic reconnect that will not happen, or a prompt loop every 10 s, both violate "clearly list the problems". |
| I31 | **A failed first `Up` lifts the block it installed.** Native tunnels install the kill switch before the adapter/routes and keep it on failure. If `Up` then fails with a live helper and no block was engaged before (`kill_switch_engaged` false, no inherited tunnel), the engine calls `Down` so that the OS and the state file agree ("not connected, not blocked"); if that `Down` fails, `kill_switch_engaged` is set so the UI reports the block and Disconnect retries. With a block already engaged (switching gateways, a crash leftover) nothing is lifted. | Previously a failed first connect could leave persistent WFP/pf/route blocks in place while the UI said "your traffic is not going through the VPN" — no Internet and no explanation. |
| I32 | **Re-JOIN refreshes endpoints.** Before every re-JOIN the session re-reads the gateway's control addresses from discovery/manual entries (new ones first, the originals kept as fallback), so a gateway that came back with a new DHCP lease is reached again instead of the session staying degraded forever. The tunnel is rebuilt (new permits) when the endpoint changed. | Addresses captured at connect time went stale after a gateway restart. |
| I33 | **macOS boot order.** `killswitch-boot` loads `/etc/pf.conf` itself when the main ruleset does not yet contain `anchor "com.apple/*"` (launchd starts our daemon and `com.apple.pfctl` in no defined order). Without it `pfInstall` would refuse and the device would boot unblocked until the app reconnected. | A boot-time hole in the one OS where the block is route-independent. |
| I34 | **Accepted residual exposures** (not fixable in the app; listed as problems where the app can see them): Android without "Block connections without VPN" — between the process being killed / a reboot and the resumed session, apps use the real IP (`android_lockdown_off` warning; the OS owns the kill switch there). macOS/Linux while blocked: an off-LAN gateway that changed its public IP cannot be re-JOINed (only the recorded endpoint and, with `allow_lan`, local networks are permitted; Windows permits `private-vpn-pro.exe` itself) — Disconnect, then Connect. Linux without fib-rule port matching: LAN resolvers stay reachable (`dns_not_blocked`). `dns_not_set` under an active kill switch now says lookups *fail* (blocked) rather than leak. | Honest reporting over false reassurance. |

## Android

| # | Decision | Why |
|---|---|---|
| I18 | The Go runtime's stdout/stderr are redirected to `/dev/null` on Android. | gomobile pipes them into logcat (`GoLog`); no-logs rule. |
| I19 | Always-on VPN start (no gateway chosen) connects to the last-used member gateway, else the first online member; never to a locked entry. | Android may start the VpnService itself. |
| I20 | Compose BOM is held at the newest line compatible with AGP 8.x / compileSdk 36; one lint check (`ForegroundServicePermission` for `systemExempted`) is suppressed. | VPN consent grants the `ACTIVATE_VPN` app-op that the platform accepts for `systemExempted`; verified on an API 35 emulator. |

## Desktop UI

| # | Decision | Why |
|---|---|---|
| I21 | Extra endpoints: `GET /api/v1/session` (re-fetch the CSRF token after a reload), `DELETE /api/v1/session` (sign out); extra SSE event `{"type":"resync"}`. | The CSRF token lives only in page memory. |
| I22 | `Sec-Fetch-Site` is enforced on every `/api/*` request, not only non-GET. | Stricter than §13.4. |

## Windows firewall

| # | Decision | Why |
|---|---|---|
| I23 | Two program-scoped UDP rules: `Private VPN Pro` (Private + Domain profiles, any remote address) and `Private VPN Pro (public, local subnet)` (Public profile, `remoteip=localsubnet`). | Windows classifies most home Wi-Fi networks as **Public**; a Private/Domain-only rule (§13.6) silently blocks phones on the same Wi-Fi. On Public networks only LAN peers are admitted, and every Private VPN Pro listener stays silent to anyone without the network key. |

## Packaging

| # | Decision | Why |
|---|---|---|
| I35 | **Windows installer** (NSIS, `build/windows/installer.nsi`, one per architecture, cross-built on Linux): per-machine into `%ProgramFiles%\Private VPN Pro` with no directory page; stops running copies (`taskkill`; a connected client stays blocked by the kill switch until it restarts), adds the firewall rules with `private-vpn-pro firewall add` while elevated, repoints an existing HKCU `Run` autostart value at the installed copy, and starts the app through `explorer.exe` so it runs unelevated. The uninstaller runs `unblock` and `firewall remove`, deletes the autostart value and asks (default No) before deleting `%LOCALAPPDATA%\Private VPN Pro`; if `unblock` fails it keeps `private-vpn-pro.exe` and says how to run it. The portable zip stays available. | The elevated helper runs the app's own executable, so it belongs in an administrator-only directory; one UAC prompt at install replaces the later firewall prompt. Moving from the portable copy while connected is not handled (the WFP permit names the old path): Disconnect first (README). |
| I36 | **macOS disk image**: `private-vpn-pro-macos-universal.dmg` (UDZO, HFS+, `Private VPN Pro.app` + `Applications` link) replaces the zip. | Standard drag-to-install; the app stays ad-hoc signed and not notarised. |
